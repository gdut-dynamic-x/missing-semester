## 一、认识ROS
### 1.1 核心定义
ROS 全称 **Robot Operating System（机器人操作系统）**，本质是**运行在Linux之上的机器人开发中间件与工具集**，并非传统桌面操作系统。它提供硬件抽象、底层设备控制、进程间消息传递、软件包管理等机器人开发通用能力。

本课程使用版本：**ROS 1 Noetic**，适配 Ubuntu 20.04，核心节点采用 C++（roscpp）开发，是 ROS 1 的最终长期支持版本。

### 1.2 三大核心组成
1.  **通信中间件**：节点间的标准交互方式，包含话题、服务、参数三类通信机制，是视觉数据流传输的核心载体
2.  **工具链**：覆盖全开发流程，包含 catkin 编译、launch 启动编排、rviz/rqt 可视化、rosbag 录包回放
3.  **软件生态**：海量开源功能包，视觉方向可直接对接 OpenCV、PCL、Eigen 等算法库，以及各类相机驱动

### 1.3 视觉视角下的ROS
ROS 为视觉开发提供了标准化的数据流转方式：相机驱动节点发布图像话题 → 识别算法节点订阅并处理 → 输出结果话题供下游决策/控制节点使用。每个模块独立解耦，便于分工开发与调试。

> 核心记忆点：**节点（执行功能的进程） + 话题（传递数据的通道）** 是 ROS 最基础的两个概念，所有视觉功能都基于这两个元素搭建。

## 二、为什么使用ROS
### 2.1 六大核心优势
1.  **原生适配机器人场景**：发布订阅、坐标变换、参数管理、数据回放等机器人刚需均为原生功能
2.  **生态完善社区活跃**：绝大多数相机、算法都有现成 ROS 包，问题可快速检索解决方案
3.  **模块化便于协作**：节点间接口解耦，视觉组与控制组可并行开发；rqt_graph 可直观查看系统连接关系
4.  **C++ 原生性能可控**：核心视觉算法基于 roscpp 开发，与 OpenCV、PCL 等库接口天然兼容，无需额外封装
5.  **数据可回放复现**：rosbag 可录制现场图像与所有话题数据，后续可逐帧回放调试，解决现场问题难复现的痛点
6.  **仿真支持完善**：Gazebo 仿真环境可提前验证算法逻辑，降低实车调试的风险与硬件损耗

### 2.2 纯上位机架构（视觉相关）
队伍采用纯上位机架构：视觉识别、姿态解算、控制决策全部运行在上位机 miniPC 的 ROS 节点中，下位机仅负责帧转换与硬件兜底。
- 对视觉开发的优势：算法修改、参数调优只需重新编译上位机节点，无需烧录下位机固件，迭代效率更高
- 数据流路径：相机 → 上位机图像话题 → 视觉算法节点 → 结果话题 → 控制节点

## 三、ROS三层架构
### 3.1 三层架构与排错思路
| 架构层级 | 核心作用 | 对应排错场景 |
|----------|----------|--------------|
| 文件系统层 | 管理代码与文件的组织形式 | 找不到功能包、编译失败、头文件找不到 |
| 计算图层 | 定义节点间的协作关系 | 收不到图像话题、节点连不上、消息类型不匹配 |
| 通信层 | 负责数据的实际传输 | 图像延迟高、丢帧、带宽不足 |

排错口诀：
- 找不到包 → 检查是否 source 环境、包是否在 src 目录
- 收不到图像 → 检查话题名、消息类型是否一致
- 延迟丢帧 → 检查队列深度、带宽是否充足
- 节点闪退 → 优先查看终端红色 FATAL 报错

### 3.2 计算图五大核心元件
| 元件 | 定义 | 视觉场景举例 | 常用命令 |
|------|------|--------------|----------|
| 节点 Node | 独立运行的进程，完成单一功能 | 相机驱动节点、识别节点 | `rosnode list/info` |
| 话题 Topic | 带名称的广播通道，发布者写、订阅者读 | `/image_raw` 图像话题 | `rostopic list/echo` |
| 消息 Message | 话题上的数据结构，由 .msg 文件定义 | `sensor_msgs/Image` 图像消息 | `rosmsg show` |
| 服务 Service | 一问一答式远程调用，有请求有应答 | 单次拍照、参数校准 | `rosservice call` |
| 参数 Parameter | 全局共享的键值对配置 | 识别阈值、相机内参 | `rosparam get/set` |

### 3.3 ROS Master 核心机制
**核心原则：Master 只负责注册寻址，不传输任何业务数据，图像数据不经过 Master**
- 运行端口：默认 11311，采用 XMLRPC 协议
- 核心职能：名字注册、名字查询、承载参数服务器、节点状态监控
- `roscore` = Master + rosout 日志节点 + 参数服务器，是 ROS 系统的启动入口

### 3.4 一次话题通信的完整流程（以图像话题为例）
1.  启动 roscore，Master 在 11311 端口等待节点注册
2.  相机驱动节点启动，向 Master 注册：发布 `/image_raw` 话题，类型 `sensor_msgs/Image`
3.  识别节点启动，向 Master 注册：订阅 `/image_raw` 话题
4.  Master 将相机节点的 IP 与端口返回给识别节点（仅交互一次）
5.  识别节点主动连接相机节点，建立 TCP 连接，校验消息类型
6.  后续所有图像帧通过 TCP 直连传输，Master 不再参与

> 重要结论：Master 宕机后，已建立连接的节点可正常传输图像；仅新节点无法完成注册与连接。

### 3.5 ros_control 控制框架
核心设计思想：**控制器算法与硬件接口解耦**
- 输入：视觉输出的位置、速度等控制指令话题
- 中间层：官方通用 Controller + 自定义 RobotHW 硬件接口
- 输出：底层硬件指令
- 对视觉开发的意义：只需按标准格式输出控制话题，无需关心底层硬件实现，专注算法本身即可
